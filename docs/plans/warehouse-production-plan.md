# План: страница «Склад и производство» (/production)

**СТАТУС: APPROVED** — финальный гейт /autoplan пройден 2026-07-18 (полный скоуп v1,
what-if слайдер включён). Ветка: main.

## Цель

Отдельная admin-страница `/production` поверх боевой ERP (READ-ONLY):

1. Анализ склада по товарам: текущие остатки, приход, продажи.
2. Прогноз спроса на следующий месяц (статистическая модель: база + сезонность + тренд).
3. Рекомендация «что и сколько производить» с учётом настраиваемого времени переналадки
   (смена продукции/вкуса) и производственной мощности.
4. План производства на следующий месяц: партии, порядок, переналадки, загрузка + AI-разбор.

Пользователь: владелец/администратор. Роль `user` (территориальная) доступа НЕ имеет.

## Премисы (подтверждены пользователем, гейт D1 2026-07-18)

1. **Производство = приход `INP` по реальным складам**; из остатка/прихода по умолчанию
   исключены `'006'` ֆիկտիվ (учётный артефакт) и `'011'` խотан (БРАК/дефект — не
   продаётся); список настраиваемый. В UI колонка честно называется
   «Приход», а не «Производство» — данных, отделяющих собственный выпуск от закупки,
   в БД нет (`PRODUCTS.fPRODUCER` пуст у всех 760 активных товаров — проверено).
2. **Спрос = продажи − возвраты**; дефицитные периоды занижают историю — принято как
   ограничение, смягчается флагом «возможен дефицит» (см. Прогноз).
3. **Переналадка = настраиваемые часы при смене семейства** (по умолчанию семейство =
   товарная группа, переопределяется маппингом) + отдельный параметр внутригрупповой
   переналадки (по умолчанию 0 ч).
4. **Охват рекомендаций**: фильтр «производственные группы» (мультивыбор в настройках,
   по умолчанию — все группы); закупные категории владелец исключает в два клика.

## Прогноз спроса (pure Python, зависимости не добавляются)

- **Якорь окон**: все forecast-SQL параметризованы `as_of_month` (НЕ константа
  `GETDATE()`): окна режутся строго `fDATE < as_of_month_start`. Для текущего прогноза
  `as_of_month` = следующий месяц; для WAPE-бэктеста — прошлый (без утечки будущего;
  синтетический тест на look-ahead обязателен).
- **База**: средние месячные нетто-продажи (`SALES − RET`, формула верифицирована
  данными) за 12 полных месяцев до `as_of_month`.
- **Сезонность**: ШТУЧНАЯ (не денежная — сезонность выручки ≠ сезонность штук),
  по товарной группе, отдельной новой функцией: `m_qty × 12 / total` строго при
  полных 24 месяцах истории группы; иначе — глобальная штучная сезонность
  (существующую денежную функцию /plans не трогаем).
- **Тренд**: МНК-линрегрессия по 6 полным месяцам, тренд-фактор ограничен ±30%.
  ⚠️ КРИТИЧНО (баг найден и исправлен при реализации 2026-07-18): тренд считается по
  ДЕСЕЗОНАЛИЗИРОВАННОМУ ряду (каждый месяц делится на его сезонный коэффициент). Иначе
  сезонность (коэффициент целевого месяца) и тренд ДВАЖДЫ считают один и тот же
  сезонный подъём — в разгар сезона прогноз завышался на +20…+83% и превышал любой
  реальный месяц. После фикса WAPE-бэктест упал с ±35% до ±21%.
- **Прогноз** = база × сезонный коэффициент × десезонализированный тренд-фактор, но
  не выше **1.5× лучшего месяца за последние 12** (потолок правдоподобия — страхует от
  остаточного завышения на товарах с короткой историей, где база≈максимум).
- **Гейт по классам (защита доверия)**: авторекомендации — только для классов A и B;
  ABC считается ПО ВЫРУЧКЕ (`SUM(sd.fSUM)`, не по штукам — суммировать литры со
  штуками нельзя, и дорогие малотоннажные SKU не должны падать в C); A=80%, B=15%.
  Хвост C — «нет надёжного прогноза», без прескриптива. Товары «вне складского
  контура» (движение только через '006') — исключены из прескриптива всегда.
- **Мало истории**: <6 мес — среднее по доступным × сезонность; <2 мес — «нет прогноза».
- **Флаг дефицита**: месяц с нулевыми продажами при ненулевых в ≥60% остальных месяцев
  помечается «возможен дефицит» и исключается из базы среднего (защита от
  самоусиливающегося недопроизводства).
- **Страховой запас**: k × σ(мес. нетто-продаж, 12 мес), k настраиваемый (default 0.5).
- **Точность**: WAPE по классу A и B агрегированно (backtest: прогноз прошлого месяца,
  посчитанный по данным до него, против факта). Средний по-SKU MAPE НЕ показываем —
  на хвосте он бессмысленно велик и подрывает доверие.

## Рекомендация производства (детерминированная, семантика order-up-to)

```
stock_now      = остаток по невыключенным складам (агенты — отдельно, в покрытие не входят)
stock_start    = max(0, stock_now − forecast_тек_месяца × доля_оставшихся_дней_тек_месяца)
                 # проекция остатка на начало целевого месяца: без неё рекомендация
                 # зависела бы от дня запуска расчёта (5-го vs 28-го числа)
target_end_stock = forecast_daily × target_cover_days + safety_stock   # остаток НА КОНЕЦ месяца
production_qty = max(0, forecast_месяца + target_end_stock − stock_start)
```

Проекция остатка — явное допущение (плановый приход текущего месяца неизвестен),
показывается в тултипе «как посчитано». Все количественные значения из БД приводятся
`float()` на границе (pyodbc отдаёт `Decimal` для `money`; `Decimal + float` = TypeError)
с `or 0` для NULL-агрегатов. Остатки джойнятся LEFT JOIN + `COALESCE(qty, 0)` к набору
прогноза: товар с продажами, но без строки в `HIRESTSTORAGES`, ОБЯЗАН появиться как
critical со stock=0 (тест обязателен).

- `target_cover_days` — целевой остаток на конец месяца в днях спроса (default 10);
  UI явно показывает «подразумеваемый остаток на конец месяца: N шт ≈ D дней».
- Кламп затоваривания: если `stock_wh` уже > `overstock_cover_days` дней — рекомендация 0
  и статус `overstock`.
- Статусы покрытия: `critical` (< critical_cover_days), `ok`, `overstock`.

## План производства с переналадками

Настройки в `production_settings.json` (gitignored; тот же паттерн, что
`ai_analysis_settings.json` — переживает деплойный `git reset --hard`). Редактирование
ТОЛЬКО через модалку настроек с валидацией; в UI видна дата последнего изменения.

```json
{
  "excluded_storages": ["006"],
  "production_groups": [],                  // пусто = все группы
  "include_agent_stock": false,
  "changeover_hours_default": 2.0,
  "changeover_hours_by_family": {"<код>": 1.0},
  "intra_family_changeover_hours": 0.0,     // смена вкуса внутри семейства
  "family_map": {},                          // PrdctGrp → семейство переналадки; пусто = группа и есть семейство
  "lines_count": 1,                          // параллельные линии (простой множитель мощности)
  "work_days_per_month": 22,
  "shift_hours_per_day": 8,
  "production_rate_by_group": {},            // шт/час; пусто = временная раскладка не строится
  "production_rate_by_product": {},
  "target_cover_days": 10,
  "safety_k": 0.5,
  "critical_cover_days": 7,
  "overstock_cover_days": 45
}
```

Алгоритм (детерминированный, порядок ЗАФИКСИРОВАН — «дефицит vs переналадки» решается
двухуровневым правилом, покрывается синтетическим тестом):
1. Кандидаты: товары классов A/B из производственных групп с `production_qty > 0`.
2. Кандидаты кластеризуются по семейству переналадки (default = товарная группа;
   маппинг переопределяется). КЛАСТЕРЫ упорядочиваются по минимальным дням покрытия
   внутри кластера (самый горящий кластер первым); ВНУТРИ кластера — по дням покрытия.
   Смена семейства = `changeover_hours` (по семейству или default); внутри семейства =
   `intra_family_changeover_hours` (default 0).
3. **Режим по умолчанию — только объёмы** («сколько произвести»). Временная раскладка
   (часы, дни, загрузка мощности) строится ТОЛЬКО когда заполнены production_rate —
   это осознанный дефолт, а не деградация: без реальных норм временной план = GIGO.
4. При заполненных rate: бюджет мощности = `lines_count × work_days × shift_hours`;
   жадное заполнение по худшему покрытию; переполнение → хвост помечен «не помещается
   в месяц» с рекомендацией (доп. смены / перенос).
5. UI явно показывает строку допущений: «модель: N параллельных линий, переналадка при
   смене семейства; реальное расписание цеха не моделируется».
6. Выход: партии (порядок, товар, объём, часы, накопительные дни), сводка: партий,
   переналадок, часов переналадки, загрузка %.

## AI-разбор (существующий паттерн, ограниченная роль)

`POST /api/production/ai-plan` — SSE-стрим по образцу `/api/managers/kpi/health/ai`
(app_v2.py:5632): `anthropic` с мягкой деградацией, модель `claude-opus-4-8`.
Роль AI — **«объясни цифры на экране»**, не самостоятельный планировщик:
- вход: агрегаты (прогнозы, остатки, партии, настройки), без PII;
- системный промпт запрещает придумывать количества и товары, не присутствующие
  во входных данных; требует ссылаться на переданные цифры;
- в UI подпись: «AI-разбор — пояснение к расчёту, не команда производству».
Сервер сам пересобирает агрегаты по параметрам scope — клиент не может внедрить
произвольный текст в промпт.
